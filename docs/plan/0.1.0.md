# blaze-cache-wasm — v0.1.0 project plan

**Version:** `0.1.0`
**Date:** 2026-11-22
**Status:** M1–M3 complete; M4 (0.1.0 tag) pending
**Repository:** standalone Rust crate (this repository)

---

## Why this project exists

Blaze Cache's current Wasm bindings live inside the monorepo at
`blaze-cache/crates/blaze-cache-wasm` and are generated with `wasm-bindgen`. That crate has
served `0.2.x`–`0.4.0` well, but it couples the binding surface to one generator's glue and
to the monorepo's release cycle.

This new project is the **future binding layer**. It is independent:

* it does **not** depend on `crates/blaze-cache-wasm`;
* it does **not** depend on the `wasm-bindgen` glue used there — no `wasm-bindgen`, `js-sys`,
  `serde-wasm-bindgen` or `wasm-bindgen-test` dependency is selected at 0.1.0;
* it owns its own toolchain, version ladder and release cadence.

The ABI is a decision to make in this release, not a dependency to inherit.

## Scope of 0.1.0

A foundation release: establish a buildable, safe, testable crate and a written decision on the
binding strategy. **No public cache API is promised yet.**

1. **Standalone crate.** Cargo package `blaze-cache-wasm` `0.1.0`, edition 2021 (see the lint note below), host + `wasm32-unknown-unknown` builds, `rustfmt`/`clippy` in the toolchain file.
2. **Safety policy from day one.** `#![deny(unsafe_code)]` with a single documented exception for the `#[no_mangle]` flat-ABI export — Rust's current lint classifies that attribute as unsafe code, so `forbid` is impossible without generated glue. There are no `unsafe` blocks or calls. Host input is copied into an arena before Rust reads it (ADR-0001 Approach B); release panics abort.
3. **ABI decision record.** [ADR-0001](../decisions/0001-abi-strategy.md) provisionally selects a flat raw ABI specified by the [`blaze.loom`](../decisions/blaze.loom) schema. The [M3 spike](../decisions/m3-spike.md) confirmed it.
4. **Minimal exported surface.** Only `ABI_VERSION` is public in 0.1.0. It starts at `0` (= `loom-abi-v1`), is exported as `__blaze_abi_version()`, and is checked by `js/abi-check.mjs` before any other call.
5. **Green baselines.** `cargo test`, `cargo build --target wasm32-unknown-unknown`, `cargo fmt --all --check`, `cargo clippy --all-targets -- -D warnings`, `node js/abi-check.mjs`.

## Non-goals for 0.1.0

* Reimplementing the cache engine (keys, TTL, SIEVE, tags, persistence) — that remains `blaze-cache-core` or its successor.
* A TypeScript/npm package, wasm-pack build scripts, or a browser test harness.
* Migrating existing consumers off the monorepo's bindings. 0.1.0 changes no runtime behavior for anyone.
* Picking a binding generator "because that is what the old crate used".

## ABI decision — options and criteria

The central 0.1.0 decision is how JS and Rust talk. Options to evaluate:

| Option | Strengths | Costs / risks |
|---|---|---|
| Generated glue (e.g. a newer `wasm-bindgen` line) | Mature tooling, familiar TS types | Reintroduces the coupling this project escapes; generator version skew |
| Flat raw ABI (stable `(ptr, len)` exports + hand-written JS decoder) | No generated glue, explicit validation, small binary | More hand-written JS; every view must respect `memory.grow` |
| Flat raw ABI + schema-driven build-time generator (Loom) | Explicit validation, generated TS later, no Rust dependency | Generator is still a tool to version; schema discipline required |
| WebAssembly Component Model / WIT | Language-neutral interface, typed contracts | Toolchain churn; browser runtime support still uneven |

Decision criteria, in priority order:

1. **Safety** — no unchecked host pointers, no `unsafe` in Rust, view lifetimes documented.
2. **Portability** — works in browsers and Node/Wasm runtimes without a second build.
3. **Binary size & cold start** — small `.wasm`, no heavyweight glue.
4. **DX** — typed TS surface, debuggable errors, stable versions.
5. **Independence** — no compile-time dependency on the monorepo's current binding crate.

## Risks

* **Toolchain churn** — Wasm Component Model support changes quickly; mitigate by keeping the public ABI small and versioned.
* **View detachment** — `memory.grow` detaches JS views; whatever ABI wins must document pointer-vs-view lifetimes.
* **Version skew** — a host compiled against a different `ABI_VERSION` must fail loudly; never silently misdecode.
* **Scope creep** — 0.1.0 is a foundation; engine work and consumer migration belong to later versions.

## Definition of done

`0.1.0` is done when the crate builds for both targets, the ABI decision is recorded with M3
evidence, all safety guardrails are in place, and nothing has changed the behavior of the existing
Blaze Cache users.
