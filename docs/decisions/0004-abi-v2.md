# ADR-0004: loom-abi-v2 (D3, D6, D7)

**Status:** accepted for 0.2.0
**Date:** 2026-11-24
**Deciders:** blaze-cache maintainers
**Relates to:** [v0.2.0 plan](../plan/0.2.0.md), [ADR-0001](0001-abi-strategy.md) (strategy, v1 reasoning), [`blaze-v2.loom`](blaze-v2.loom) (the contract), [engine provenance](engine-provenance.md)

## Context

0.1.0 froze `blaze.loom` as `loom-abi-v1` and pinned `ABI_VERSION = 0`. The v1 schema was
written before the engine was inspected and is wrong in three places the 0.2.0 evidence table
([plan §Evidence](../plan/0.2.0.md)) documents: `CacheConfig` assumes a `max_bytes` budget and a
cache-wide TTL the core does not have, `EvictionPolicy { Lru, Lfu, Fifo }` names policies the
core does not implement, and `Stats` has five fields where `CacheStats` has seven different ones.

Three decisions settle how v2 relates to v1 and to the real engine:

* **D3 — schema version.** Amend the tagged v1 file, or write a new schema?
* **D6 — eviction.** Ship an enum the engine cannot honour, or a truthful one?
* **D7 — stats.** Shrink the core's stats to the schema, or widen the schema to the core?

## Decisions

### D3 — new schema file, `ABI_VERSION = 1`

**Option (b): `blaze-v2.loom` is added; `blaze.loom` stays byte-for-byte as tagged in 0.1.0.**

The version check exists precisely for this. Rewriting a tagged decision artifact is worse than
one loud bump, and a host compiled against v1 must fail the check rather than silently misdecode
a config struct that changed shape. `ABI_VERSION = 1` corresponds to `loom-abi-v2` and stays `1`
for the whole 0.2.0 line; any signature change after tagging bumps to `2` in 0.3.0. ADR-0001
gains a v2 section pointing here instead of being rewritten — its v1 reasoning stays intact.

### D6 — truthful single-variant enum

**Option (a): `enum EvictionPolicy { Sieve }`.**

The core has no `EvictionPolicy` type; eviction is a fixed SIEVE implementation
(`eviction.rs:25`). Lru/Lfu/Fifo are **removed from the schema, not implemented**. An inaccurate
contract is worse than a single-variant enum: every consumer that branches on `Lru` would be
branching on a lie. When the engine grows real policy choice, v3 adds variants.

### D7 — schema superset matching `CacheStats`

**Option (a): the 7-field superset; never shrink the core.**

v2 `Stats` is a fixed-layout 56-byte struct, seven little-endian `u64` fields in this exact
order: `hits, misses, evictions, expirations, invalidations, size, capacity`. `size` and
`capacity` are **entry counts**. The core's `usize` fields widen to `u64` — safe on both 32- and
64-bit hosts, and a fixed-width ABI field is mandatory anyway. v1's `bytes` and `entries` fields
do not exist in the core and are dropped, not invented.

## Consequences

* `blaze.loom` (v1) is immutable history; `blaze-v2.loom` is the 0.2.0 contract. Both are
  committed; only v2 has exports against it.
* `ABI_VERSION = 1` is pinned in Rust, JS (`js/abi-check.mjs`) and CI; a deliberate mismatch
  throws.
* Consumers can trust the schema: `Sieve` means SIEVE, `capacity` means entries, config fits in
  8 bytes because the core's config is two `u32`s.
* The v1 → v2 diff is the honest list of what inspection changed — config shape, eviction truth,
  stats width — recorded here rather than discovered during implementation.
